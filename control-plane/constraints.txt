# The Community image's lock: every package of the environment the image
# ships (`Dockerfile`: `pip install -c constraints.txt ...`), pinned exactly,
# pip, setuptools and wheel included (they are copied into the image too).
# `scripts/third_party_licenses.py generate` fails the build when the
# installed environment is not exactly this list, and the repository's
# `THIRD_PARTY_LICENSES` is generated from it (`tests/test_third_party_licenses.py`
# holds the two equal). The ranges in `pyproject.toml` stay the contract; this
# file is the resolution of them the image ships.
#
# The images are Linux (python:3.13-slim) on amd64 and arm64, and this is
# what their install resolves to there. It is not what a Mac resolves to:
# SQLAlchemy needs greenlet on x86_64 and aarch64 only, so greenlet is
# pinned here although a macOS arm64 install does not have it. (A constraint
# installs nothing by itself: `pip install -c constraints.txt .` on a Mac is
# unaffected.) The pins carry no environment markers: the licence step reads
# `name==version` lines only, and both image platforms install the same set.
#
# Refresh deliberately, then record the Linux resolutions and regenerate the
# licences:
#   python3.13 -m venv /tmp/lock && /tmp/lock/bin/pip install --upgrade pip setuptools wheel \
#     && /tmp/lock/bin/pip install . && /tmp/lock/bin/pip freeze --all --exclude brutor-agent-control-plane
#   (add what only Linux installs, from the recording below)
#   scripts/record_linux_resolution.sh          (Docker: linux/amd64 and linux/arm64)
#   python scripts/third_party_licenses.py regenerate community
# `tests/test_third_party_licenses.py` holds this file equal to both
# recordings (`tests/fixtures/linux_resolution/`).
