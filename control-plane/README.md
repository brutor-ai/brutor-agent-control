# Brutor Agent Control — Control Plane (Community Edition)

The configuration and administration backend of Brutor Agent Control: a
Python/FastAPI service that owns the database schema and serves the admin
API the Admin Console talks to. It writes configuration — the tenant, admin
users and roles, API keys, LLM models and routing, MCP servers, A2A agent
cards, skills, resource groups, guardrails, approvals, compliance evidence —
and the gateway (`brutor-gateway-core`, Rust) reads it and carries all
runtime traffic.

**This repository's root package is the Community Edition.** The Enterprise
Edition is a second package in [`enterprise/`](enterprise/README.md) that
adds features to the same application; nothing in the Community package
imports it.

Documentation for users and operators is at <https://docs.brutor.ai>.

## The two packages

| | Community | Enterprise |
|---|---|---|
| Distribution | `brutor-agent-control-plane` (`pyproject.toml`) | `brutor-agent-control-plane-enterprise` (`enterprise/pyproject.toml`), depends on the Community one |
| Python package | `app` | `brutor_enterprise` |
| Application factory | `app.app:create_app` | `brutor_enterprise.app:create_app` |
| Entry point | `python main.py`, console script `brutor-agent-control-plane` | `python enterprise/main.py`, console script `brutor-agent-control-plane-enterprise` |
| Image | `Dockerfile` | `enterprise/Dockerfile` |

Enterprise adds: tenant management and the system administrator
(`multi_tenant`), the Knowledge Base, the response and prompt caches,
Policy-as-Code, traffic import, discovery, the MCP Registry, model and MCP
server deployment (Docker, Kubernetes), batch jobs and the User Portal's
administration. The edition of a running process is
the application factory it was started with; there is no flag.

## Prerequisites

- Python 3.13
- PostgreSQL 16 and Redis or Valkey (`docker compose up -d` starts a
  development pair from `docker-compose.yml`)
- The gateway, `brutor-gateway-core`, for anything beyond configuration: it
  shares this database, `JWT_SECRET` and `ENCRYPTION_KEY`

The Community Edition needs no licence key, no Qdrant and no object store.

## Configuration

Configuration is read from the environment; a `.env` file in the working
directory is loaded at start (a variable that is already set keeps its
value). Every variable is defined once, in `app/env_vars.py` (name, type,
default, whether it is required or a secret, what it accepts), and read
through its definition; nothing else reads the environment. `.env.example`,
the table below and the first-start table of the
[getting-started guide](docs/getting-started-guide.md) are generated from
those definitions (`python scripts/gen_env_docs.py`), and
`python main.py --print-env` prints them as JSON.

A start checks the environment before it does anything else and refuses it,
one line per name and never a value, for:

- a value that is not of its variable's type: a boolean is one of `true`,
  `false`, `1`, `0`, `yes`, `no`, `on`, `off`; a number is written in
  digits; a value with a closed list of choices is one of them. A malformed
  value never becomes the default;
- a required variable that is not set.

A `BRUTOR_*` variable that is set and that this edition does not read is
named in a warning at start and has no effect (a container platform sets
such names for its service links; a setting of the Enterprise Edition is one
too).

## Run

Development (uvicorn, one process). The PostgreSQL driver (`psycopg2`) is built from source against the system's libpq, so
`pip install` needs `pg_config` on the `PATH` and a C compiler: on macOS
`brew install libpq` and `export PATH="$(brew --prefix libpq)/bin:$PATH"` (Xcode's command line
tools for the compiler); on Debian or Ubuntu `apt-get install libpq-dev gcc python3-dev`.

```bash
pip install -e ".[dev]"
cp .env.example .env              # then fill in the required values
python main.py                    # http://localhost:5050
python main.py --help             # options: --listen-addr, --reload, --sql-echo, ...
python main.py init               # only create the schema and seed, then exit
python main.py --print-env        # every environment variable, as JSON
```

Production (gunicorn):

```bash
./start_with_gunicorn.sh community
# which is: gunicorn app.app:create_app --config gunicorn.conf.py
```

The Enterprise Edition: `python enterprise/main.py`,
`./start_with_gunicorn.sh enterprise`.

`python main.py edition-reset` deletes the Enterprise Edition's data from a
database Enterprise has used, so that the Community Edition starts on it (a
Community start refuses such a database and says so). It is a dry run unless
given `--confirm-delete-enterprise-data`.

`python main.py admin-unlock USERNAME [--tenant ID]` unlocks an administrator
(the tenant defaults to `default`): for the installation whose only
administrator is locked, where nobody is left to call
`POST /v1/admin/users/tenant/{admin_id}/unlock`. Five wrong passwords lock an
account for 15 minutes and that lock ends by itself; this ends it now. It
changes neither the password nor a deactivated account, records itself in the
tenant's admin audit log and prints no secret.

## Database and migrations

The control plane owns the schema; the gateway never changes it. Models are
in `app/database/models/`, migrations in `alembic/versions/` (configuration:
`alembic.ini`). **All models and all migrations belong to the Community
package**, including the tables only Enterprise features use: there is one
schema for both editions.

A start initialises the database under an advisory lock: `alembic upgrade
head`. An empty database gets the baseline revision (the whole schema) and
every revision after it; a database with tables but no `alembic_version` is
refused.

```bash
alembic revision -m "describe the change"   # a new revision for every schema change
alembic upgrade head
alembic current
```

More in `alembic/README.md`.

## Tests

```bash
pytest                                             # Enterprise Edition: tests/ and enterprise/tests/
BRUTOR_TEST_EDITION=community pytest tests/        # Community Edition: tests/ only
```

The Community suite (`tests/`) runs for both editions; `enterprise/tests/`
is the Enterprise Edition's own. The suites are hermetic: SQLite in memory,
no network, no running stack. Tests marked `live_api` and `live_e2e` are
excluded unless asked for.

Some tests need PostgreSQL. They run only when told where a **throwaway**
server is, and each creates and drops its own database there — never point
them at a database you keep:

```bash
BRUTOR_PG_TESTS=1 BRUTOR_PG_TEST_URL=postgresql://USER:PASSWORD@HOST:PORT/postgres pytest tests/test_edition_install_pg.py
```

The edition boundary file (`editions.yaml`) and the edition-install contract
are kept outside this repository. The tests that compare the code with them
read them from the directory `BRUTOR_EDITION_RECORDS_DIR` names; it has no
default. Not set, those tests are skipped, each saying so; set to something
that is not a directory, or a directory without the file, they fail:

```bash
BRUTOR_EDITION_RECORDS_DIR=/path/to/edition-records pytest
```

The same for the Core Gateway's source: the tests that compare a rule here
with the gateway's (the Python/Rust parity tests) read the core from the
directory `BRUTOR_CORE_REPO` names, at its committed `HEAD` when it is a git
checkout. It has no default; not set, those tests are skipped, each saying
so; set to something that is not a directory, they fail:

```bash
BRUTOR_CORE_REPO=/path/to/the/core pytest
```

The gates, all of them tests:

- coverage floors, one per edition under test and package measured
  (`[tool.coverage.report]` and `[tool.brutor.coverage-floors]` in
  `pyproject.toml`; `tests/coverage_floors.py` fails a run below one):

  ```bash
  pytest --cov=app --cov=brutor_enterprise                 # Enterprise mode: app 82 %, brutor_enterprise 73 %
  BRUTOR_TEST_EDITION=community pytest --cov=app tests/    # Community mode: app 80 %
  ```
  (`pytest --cov=app` alone holds `app` to the Enterprise-mode floor, as before);
- the recorded OpenAPI document of the Community Edition
  (`tests/fixtures/openapi_snapshot_community.json`; re-record on purpose with
  `BRUTOR_UPDATE_COMMUNITY_OPENAPI_SNAPSHOT=1 pytest tests/test_community_openapi_snapshot.py`),
  and no two models sharing a class name. The Enterprise Edition's document is
  under `enterprise/` (`enterprise/README.md`);
- the recorded principal matrix (who may call which route) and the recorded
  install seed of each edition;
- the edition boundary: no Community module imports an Enterprise one, a
  Community start loads no Enterprise module or library, and Community code
  names an Enterprise-only table only where listed
  (`tests/test_edition_import_guard.py`, `test_community_import_probe.py`,
  `test_edition_table_guard.py`);
- packaging: each package declares exactly what its code imports
  (`tests/test_packaging.py`).
- a model row has a destination: one with no `api_url`, of a provider the
  gateway knows no base URL for, is refused when it is saved, and the list
  of such providers is the gateway's, read from its source where it is
  checked out (`tests/test_model_destination_rule.py`);
- no log, coverage database or environment file is tracked
  (`tests/test_no_tracked_run_output.py`);
- the two packages have one version, the platform's
  (`tests/test_distribution_version.py`);
- no file uses a name it neither defines nor imports
  (`tests/test_undefined_names.py`, pyflakes);
- a refused request keeps only what it committed on purpose. The suite's
  SQLite database is one connection shared by every session, on which another
  session's commit (the audit trail's) also commits what a request had only
  flushed; a test in which that happens and the request then refuses has seen
  a state no server would be in, and fails
  (`tests/refusal_write_detector.py`, wired in `tests/conftest.py`). The cases
  themselves are held on a database with a connection per session
  (`tests/test_refusal_write_semantics.py`);
- the audit record of a success exists only for a write that was
  committed: it is written when the request's own transaction commits and
  dropped when that rolls back; the record of a refusal is written at once
  (`tests/test_audit_after_commit.py`, on the same kind of database);
- a test under `tests/` asserts the same whether or not the checkout has
  `enterprise/`: Enterprise cases are in `enterprise/tests`
  (`tests/test_app_factory.py`).

A recording changes only on purpose; each test says how to re-record it.

## Docker images

```bash
docker build -t control-community .                                # Community
docker build -f enterprise/Dockerfile -t control-enterprise .      # Enterprise (same build context)
scripts/smoke_images.sh --community control-community --enterprise control-enterprise
```

The Community image is built from a context without `enterprise/`, carries
the sources and the Community dependencies only, and runs
`gunicorn app.app:create_app`. The smoke script starts each image against a
PostgreSQL and a Redis and checks what only a running image can show.
